## Story
**Como** plataforma multi-tenant,
**quero** um schema Postgres com os enums e tabelas fundacionais e RLS habilitada em toda tabela com `tenant_id`,
**para que** nenhum dado de um tenant seja acessível por outro desde a primeira linha de código escrita (Decisão A1, §6.2).

## Acceptance Criteria
1. Enums criados exatamente como especificado em §17.1: `lead_status`, `lead_origem`, `canal_provider`, `remetente`, `conversa_estado`, `tipo_entrada`.
2. Tabelas `tenants` e `tenant_membros` criadas conforme §17.2, com `papel` restrito a `dono | atendente | operador`.
3. RLS habilitada em `tenants` e `tenant_membros` (as únicas tabelas de domínio criadas nesta story), com policy de pertencimento via `tenant_membros` (padrão de §17.11) — S1 (§22): nenhuma policy `using (true)`. Toda tabela de domínio criada em stories posteriores replica este mesmo padrão como parte do seu próprio DoD — não é reaberto aqui.
4. Teste de integração confirma que uma sessão autenticada como membro do tenant A não lê nem escreve `tenant_membros` do tenant B (T-RLS, §23.1, escopo desta story).
5. Migration aplicada e confirmada no Supabase antes de qualquer story subsequente iniciar (DoD §27.2).

## Dev Notes

### Contexto de arquitetura
Multi-tenant desde o dia 1 é decisão A1 (§6.2), não negociável. Esta story é o alicerce de **todas** as demais — nenhuma outra story pode iniciar (per EPIC-1, docs/prd/epic-1-fundacao.md) até esta estar em `Done`.

### Um tenant hoje, N amanhã — não é uma migração futura, é a mesma arquitetura desde o Task 1
Nenhuma tabela do PRD (aqui ou em qualquer story posterior) tem uma versão "single-tenant" e outra "multi-tenant" — todas nascem com `tenant_id` e RLS, inclusive `canais` (2.3/2.4), `wl_integracao` (5.1) e `ia_config` (8.1), que já são `primary key (tenant_id, ...)` no schema literal do PRD. Isso significa que ligar um segundo cliente no futuro é **inserir uma segunda linha** em `tenants` + suas credenciais próprias — não é reescrever schema nem "migrar" nada. A decisão A1 já é isso: "Produto nasce para escalar por indicação" (§6.2), e §20 já fixa a meta como requisito não funcional: NFR6 "≥100 conversas simultâneas por tenant", NFR7 "≥50 tenants por instância do worker".

**O que muda entre agora e o futuro multi-cliente não é código, é processo:** hoje (Task 6 desta story) o tenant piloto é inserido manualmente, porque o wizard de onboarding (story 8.3, "Onboarding de tenant") ainda não existe neste ponto do backlog. Quando o segundo cliente chegar, 8.3 já estará pronta e o processo deixa de ser manual. Não há trabalho de "preparar para SaaS" pendente além de terminar o backlog na ordem em que está — a arquitetura já é SaaS.

### Schema (fonte literal: PRD §17.1, §17.2)
```sql
create type lead_status as enum (
  'novo','qualificando','orcamento','follow_up','negociando','agendado','ganho','descartado'
);
create type lead_origem as enum (
  'whatsapp_organico','instagram','indicacao','google','campanha','manual'
);
create type canal_provider as enum ('uazapi','meta');
create type remetente as enum ('lead','ia','atendente','sistema');
create type conversa_estado as enum ('ia','pausada','transbordo');
create type tipo_entrada as enum ('primeiro_contato','continuacao','retomada','reengajamento');

create table tenants (
  id uuid primary key default gen_random_uuid(),
  nome text not null,
  slug text unique not null,
  cidade text, uf text,
  ativo boolean not null default true,
  criado_em timestamptz not null default now()
);

create table tenant_membros (
  tenant_id uuid not null references tenants(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  papel text not null default 'atendente',
  primary key (tenant_id, user_id)
);
```

### Padrão de RLS (fonte literal: PRD §17.11)
```sql
alter table leads enable row level security;
create policy leads_tenant on leads for all
  using  (tenant_id in (select tenant_id from tenant_membros where user_id = auth.uid()))
  with check (tenant_id in (select tenant_id from tenant_membros where user_id = auth.uid()));
```
O worker acessa via service role com filtro explícito por `tenant_id` em toda query — não depende de RLS para si mesmo, mas RLS protege o acesso via portal/anon key.

### Dois problemas reais encontrados durante a implementação (importante para as próximas stories)

**1. Recursão infinita na policy de `tenant_membros` (ERRO 42P17).** A primeira versão da policy fazia `tenant_membros` consultar a si mesma dentro do próprio `USING`/`WITH CHECK` — Postgres reaplica a mesma policy RLS ao avaliar a subconsulta, gerando loop infinito. Qualquer `SELECT` na tabela quebrava. Corrigido com uma função `SECURITY DEFINER` (`current_tenant_ids()`) que resolve o conjunto de tenants do usuário atual sem reacionar a RLS de `tenant_membros`. **Isso só acontece quando uma tabela consulta a si mesma dentro da própria policy** — o padrão literal do PRD em §17.11 (tabela `leads` consultando `tenant_membros`, uma tabela diferente) não tem esse problema. Só `tenant_membros` precisa do helper; as demais tabelas de domínio podem seguir o padrão literal do PRD sem alteração.

**2. Função `SECURITY DEFINER` exposta como endpoint público (WARN do `get_advisors`).** Ao criar `current_tenant_ids()` em `public`, o PostgREST expôs automaticamente `/rest/v1/rpc/current_tenant_ids` para qualquer usuário autenticado chamar diretamente. Não era o uso pretendido (é uso interno da policy). Corrigido movendo a função para um schema `private` (criado nesta story), que o PostgREST não expõe — `get_advisors(security)` foi de 2 WARN para 0.

**Diretriz para stories futuras:** ao criar qualquer função `SECURITY DEFINER`, colocá-la em `private.*`, nunca em `public.*`, a menos que deva mesmo ser chamável via API. Referenciar `private.current_tenant_ids()` em vez de repetir o subselect cru sempre que uma policy precisar do conjunto de tenants do usuário atual.

**Verificação executada (não simulada):** criei 2 tenants e 2 usuários reais em `auth.users`/`tenants`/`tenant_membros`, simulei a sessão do usuário A via `set local role authenticated; set local request.jwt.claim.sub = '<uuid>'` (mesmo mecanismo que `auth.uid()` usa em produção), confirmei que ele só enxerga o próprio tenant em `SELECT`, confirmei que a tentativa de `INSERT` cruzando para o tenant B é rejeitada com `42501`, e removi os dados de teste em seguida. Rodado duas vezes — antes e depois da correção do schema `private`, para não validar contra uma versão descartada da policy.
