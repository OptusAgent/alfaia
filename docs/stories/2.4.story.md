## Story
**Como** tenant que opera com o canal oficial Meta,
**quero** um adapter AuctaFlux/BSP com validação HMAC obrigatória,
**para que** o envio oficial funcione sem risco de banimento e com a janela de 24h respeitada (§14.1, §14.4).

## Acceptance Criteria
1. Implementa `CanalAdapter` (de 2.1) para AuctaFlux: `enviar_texto` → `POST /workspaces/{id}/messages`; `enviar_midia` → `POST /workspaces/{id}/messages/media`; `enviar_template` → `POST /workspaces/{id}/messages/template` (AC 14.2, rotas confirmadas via README do pacote `@auctaflux/reseller-mcp`, não via a doc site — ver Dev Notes).
2. Webhook recebido (`forward_to_url`) tem HMAC validado; inválido → 401, captura o corpo cru em `webhook_capturas` (via 2.2) e **não persiste em `conversas`/`mensagens`** (AC 14.3, C1).
3. Payload normalizado estruturalmente idêntico ao do UAZAPI (AC 14.2).
4. `capabilities` retorna `janela_24h=True`, `suporta_template=True`, `requer_delay=False`.
5. Canal Meta com janela de 24h fechada bloqueia texto livre **server-side** (não só na UI) — AC 14.5, consultado via `capabilities` pelo motor (§14.3, último parágrafo).

### O que é confirmado (fontes: `MCP_CONECTION_AUCTA.md`, README do pacote `@auctaflux/reseller-mcp` no npm — ambos lidos nesta sessão)
- Autenticação: API key formato `aflx_rsl_...`, "reseller" — uma chave controla todas as instâncias (`AUCTAFLUX_RESELLER_API_KEY`).
- Base URL configurável via `AUCTAFLUX_BASE_URL` (exemplo documentado: `https://api-flux.aucta.tech`).
- Conceito central: **workspace** = instância/número WhatsApp.
- Rotas REST (mapeadas 1:1 a partir das ferramentas do MCP wrapper, que é um proxy fino sobre a REST API):

| Ferramenta MCP | Método | Rota |
|---|---|---|
| list_instances | GET | `/workspaces` |
| get_instance | GET | `/workspaces/{id}` |
| create_instance | POST | `/workspaces` |
| update_instance | PATCH | `/workspaces/{id}` |
| archive_instance | DELETE | `/workspaces/{id}` |
| get_connection_status | GET | `/workspaces/{id}/connection` |
| create_connect_link | POST | `/workspaces/{id}/connect-link` |
| register_connection | POST | `/workspaces/{id}/connection/register` |
| disconnect_connection | DELETE | `/workspaces/{id}/connection` |
| rotate_forward_secret | POST | `/workspaces/{id}/rotate-secret` |
| send_text_message | POST | `/workspaces/{id}/messages` |
| send_template_message | POST | `/workspaces/{id}/messages/template` |
| send_media_message | POST | `/workspaces/{id}/messages/media` |
| send_interactive_message | POST | `/workspaces/{id}/messages/interactive` |
| mark_message_as_read | POST | `/workspaces/{id}/messages/{wamid}/read` |
| delete_message | DELETE | `/workspaces/{id}/messages/{wamid}` |
| list_templates | GET | `/workspaces/{id}/templates` |
| create_template | POST | `/workspaces/{id}/templates` |
| delete_template | DELETE | `/workspaces/{id}/templates?name=...` |
| get_business_profile | GET | `/workspaces/{id}/profile` |
| update_business_profile | PATCH | `/workspaces/{id}/profile` |
| get_usage | GET | `/usage` |

- Formato de erro (confirmado): `{"error": {"code": "...", "message": "..."}}`. Códigos conhecidos: `RATE_LIMIT_EXCEEDED` (1000 req/min, aguardar 60s), `WORKSPACE_NOT_FOUND`, `CONNECTION_NOT_FOUND`, `PIN_REQUIRED`, `PIN_MISMATCH`, `WORKSPACE_ARCHIVED`, `META_API_ERROR`.
- Onboarding do número: `create_instance` → `create_connect_link` (link de onboarding do cliente) → `register_connection` (PIN 2FA) → `get_connection_status`.
- Existe `rotate_forward_secret` — confirma que o HMAC do webhook (`forward_to_url`, citado no comparativo §14.1 do PRD) é baseado em um "forward secret" rotacionável.
