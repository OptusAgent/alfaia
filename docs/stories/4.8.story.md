## Story
**Como** lead conversando pelo WhatsApp,
**quero** que a IA de fato consulte o catálogo, os horários e crie meu agendamento quando decide fazer isso,
**para que** a resposta que recebo venha de dado real da WebLocação, não de texto livre do modelo (Princípio P3).

## Contexto — por que esta story existe

Durante a ativação em produção da story 5.6 (2026-08-19), @devops foi verificar o que faltava para rodar um teste conversacional real via WhatsApp sandbox e encontrou um gap maior do que a ausência de `OPENROUTER_API_KEY`. Mesmo com a chave configurada, **a IA nunca chamaria nenhuma tool de verdade**:

- `worker/app/services/openrouter_client.py::gerar_resposta` não envia nenhum schema de `tools`/function-calling no payload da API — pede só texto livre ao modelo, e só sabe ler `choices[0].message.content`.
- `worker/app/services/ai_engine.py::processar_atendimento` (linhas 187–229): quando `resposta_llm` vem preenchida, faz `texto_resposta = resposta_llm` **diretamente**. As chamadas a `tools_registry.executar_tool(...)` só existem dentro dos ramos `elif` que só executam quando **não há** resposta real do LLM — hoje isso é keyword-match no texto do lead (`"vestido" in texto_inbound.lower()`, etc.), um fallback de desenvolvimento, não uma decisão da IA.
- O teste `worker/tests/test_ai_engine.py::test_motor_usa_openrouter_quando_llm_responde` documenta e trava esse comportamento: injeta um LLM fake que retorna texto puro e afirma `res.texto_resposta == "Claro, posso te ajudar..."` sem checar `tools_executadas` — confirma que isso é o comportamento pretendido hoje, não um bug escondido.

`tools_registry.py` já tem as 8 tools de PRD §8.2 registradas com schema Pydantic validado (Task 2 da story 4.3, `Done`) e um dispatcher (`executar_tool`) que já funciona — isso não muda. O que falta é **conectar** esse registro ao ciclo real de function-calling da API: enviar os schemas como `tools` no payload, ler `tool_calls` da resposta, executar, devolver o resultado ao modelo e deixar ele formular a resposta final com base no dado real.

**Impacto:** isso invalida a premissa funcional real (não a de teste/fallback) das ACs de tool-calling em 4.3 (AC 2, AC 3, AC 5), 5.2, 5.3, 5.5 e 6.6 — todas `Done`, todas assumindo implicitamente que a IA aciona as tools durante conversa real. Nenhuma delas precisa ser reaberta por si só (o fallback determinístico cobriu os testes que cada uma escreveu), mas nenhuma delas funciona como descrito fora do fallback.

## Acceptance Criteria
1. `openrouter_client.gerar_resposta` envia as 8 tools de PRD §8.2 (a partir dos schemas Pydantic já existentes em `tools_registry.py`, convertidos para JSON Schema de function-calling) no payload da requisição à API, e retorna tanto texto quanto eventuais `tool_calls`, não só uma string.
2. Quando a resposta do LLM contém `tool_calls`, `ai_engine.processar_atendimento` executa cada uma via `tools_registry.executar_tool`, devolve o resultado ao modelo como mensagem de papel `tool`, e faz uma nova chamada para obter a resposta final — em loop, até o modelo responder só com texto (sem inventar o resultado da tool antes dela ser executada).
3. O loop de tool-calling tem um limite máximo de iterações (a definir pelo @architect na revisão — ex.: 4) para nunca travar a conversa em loop infinito; ao atingir o limite, aciona `abrir_transbordo` em vez de responder com dado não confirmado (P3, I2).
4. A resposta final da IA, quando envolve produto, disponibilidade, horário ou confirmação de agendamento, é sempre derivada do resultado real da tool (`buscar_produtos`/`consultar_slots`/`agendar`) executada nesta troca — nunca um valor, horário ou disponibilidade que não veio de uma chamada de tool bem-sucedida na conversa em curso (P3, I5, AC 8.2 de 4.3).
5. Falha ao executar uma tool (exceção, timeout do WL, erro do WebLocação) aciona `abrir_transbordo` e informa ao lead que a equipe vai confirmar — nunca deixa o modelo "inventar" um resultado plausível para a tool que falhou (AC 8.3 de 4.3, I2).
6. O fallback determinístico por keyword-match atual (`elif "vestido" in texto_inbound...`) é mantido **apenas** como caminho de desenvolvimento sem LLM configurado (`resposta_llm is None` por `OPENROUTER_API_KEY` ausente) — não como caminho concorrente quando o LLM está configurado e respondeu.
7. `test_motor_usa_openrouter_quando_llm_responde` (e qualquer outro teste que hoje assume "texto do LLM = resposta final sem tools") é atualizado para refletir o novo comportamento — cenário sem tool_calls continua funcionando igual (resposta de texto direta), cenário com tool_calls é coberto por teste novo.

## Dev Notes

### O que já existe e não muda
- `tools_registry.py`: os 8 schemas Pydantic e o dispatcher `executar_tool` — reaproveitar, não recriar.
- `weblocacao_service`/`scheduling_service`: já corrigidos pela story 5.6 para persistir de verdade — as tools que os chamam (`buscar_produtos`, `consultar_slots`, `agendar`) já vão gravar `wl_chamadas`/`agendamentos` reais quando executadas por este loop.
- O fallback determinístico continua existindo — só muda a condição em que ele roda.

### Questão técnica em aberto (não decidir sem @architect/@po)
`ia_config.modelo` tem default `deepseek/deepseek-r1-distill-llama-70b` (migration `20260817150000_s35_canais_rls_ia_model.sql`). Não está confirmado se esse modelo específico, via OpenRouter, suporta function-calling de forma confiável (modelos de "reasoning" às vezes têm suporte parcial/instável a tools). Isso não bloqueia o desenvolvimento desta story (o schema/loop é independente do modelo), mas bloqueia validar a AC 7 (teste manual E2E) até confirmar. Mesma linha da Q8 do PRD (§29) que já pairava sobre a 4.3.

### Dependência de sequenciamento (Task 7)
Tasks 1–6 são independentes e podem começar imediatamente (não dependem de nenhum PR pendente). **Task 7** (validação E2E manual) depende da story 5.6 estar mergeada em `main` — hoje 5.6 está com Status `Done` no arquivo da story, mas ainda só existe na branch local `story-5.6-wl-persistencia-real`, sem PR aberto (@devops ainda não empurrou). Se Task 7 for tentada antes disso, rodar a wl-fake-api a partir dessa branch localmente é suficiente — não é obrigatório esperar o merge, só não existe em `main` ainda.

### Escopo explicitamente fora desta story
