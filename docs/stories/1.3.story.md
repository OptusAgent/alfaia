## Story
**Como** usuário do Portal (dona da loja, atendente ou operador),
**quero** uma casca de navegação Next.js 15 (App Router) com as áreas do produto já roteadas,
**para que** cada módulo (M1–M9) tenha um lugar fixo para ser desenvolvido nas stories seguintes, sem retrabalho de layout.

## Acceptance Criteria
1. Shell Next.js 15 App Router criado com layout autenticado (usa 1.2) e rotas-esqueleto para: Kanban (E6), Conversas (E4), Agenda (E5), Base de contatos/Campanhas (E7), Configurações (E8).
2. Navegação respeita a matriz de permissões de 1.2 — item de menu não aparece se o papel não tem acesso ao recurso correspondente.
3. Portal responsivo a partir de 360px de largura (NFR13).
4. Fluxos principais de navegação atendem WCAG 2.1 AA (NFR12) — landmarks semânticos, navegação por teclado, contraste mínimo.
5. Seletor de tenant ativo (de 1.2) visível no shell para usuários multi-tenant.

## Dev Notes

### Fundamentação (§6.1 Componentes)
O shell é a camada "Portal Next.js" do diagrama de arquitetura (§6.1), consumindo Supabase Realtime para os módulos que a exigem (implementados nas stories de cada épico). Esta story entrega apenas a casca — nenhum módulo tem lógica de negócio própria aqui.

### Stack
Next.js 15 App Router, conforme `docs/framework/tech-stack.md`. Sem app mobile nativo (fora de escopo, §5.2).

### Requisitos não funcionais aplicáveis (§20)
- NFR12: WCAG 2.1 AA nos fluxos principais.
- NFR13: responsivo ≥ 360px de largura.
- NFR8 (Kanban com 500 leads ≤ 2s) não é responsabilidade desta story — aplica-se à story 6.1 (Kanban), mas o shell não deve introduzir overhead de layout que comprometa esse orçamento.

### Testing
Sem padrão explícito de §23.1 para "shell" — @po deve fundamentar esta lacuna na validação (ver Observações em docs/prd/epic-1-fundacao.md). Sugestão: teste E2E de navegação básica por papel, alinhado ao padrão "Portal | E2E" de §23.1.

### Correção de versão — Next.js 15, não 16
`create-next-app@latest` instalou Next.js 16 por padrão (é o `latest` atual do npm). `docs/framework/tech-stack.md` exige literalmente Next.js 15 — corrigido via `npm install next@15 react@19 react-dom@19` logo após o scaffold, e `eslint-config-next@15` alinhado junto. **3 vulnerabilidades HIGH conhecidas** (`postcss`, `sharp`/libvips, ambas transitivas de dependências do Next.js) não têm correção sem subir para o Next 16 — aceitas conscientemente por ora (afetam build-time e processamento de imagem, não há upload de imagem no produto ainda); reavaliar quando houver um patch 15.x ou quando a migração para 16 for uma decisão deliberada do @architect, não um efeito colateral do scaffold.

### Correção de configuração — ESLint 9 + eslint-config-next@15
`eslint-config-next@15` publica no formato legado (`{extends: [...]}`), não flat config nativo (isso só mudou na v16). O `eslint.config.mjs` gerado pelo `create-next-app` (que assumia v16) quebrava com `TypeError: nextVitals is not iterable`. Corrigido usando `FlatCompat` de `@eslint/eslintrc` — é o padrão documentado do próprio Next.js 15 para essa combinação, não uma gambiarra.

### Bug real encontrado em teste manual no navegador — RLS de `tenant_membros` não filtra por usuário
`lib/tenant.ts` fazia `select tenant_id, papel, tenants(...) from tenant_membros` sem `.eq("user_id", ...)`, assumindo que a RLS já restringia às linhas do usuário atual. **Errado**: a policy de `tenant_membros` (1.1) restringe por **tenant** (`tenant_id in current_tenant_ids()`), não por **linha/usuário** — ou seja, ela mostra corretamente todos os colegas de um tenant do qual você é membro (é para isso que serve uma tabela de membros). Descoberto porque o seletor de tenant mostrou "valmir" duplicado no teste real (o dono real e o atendente de teste, ambos no mesmo tenant, apareciam como se fossem 2 tenants do mesmo usuário). Corrigido com `.eq("user_id", user.id)` explícito em `getUserTenants()`. Nenhum dado vazou entre tenants diferentes — o vazamento era "ver colega do mesmo tenant", não "ver tenant de outro".

### Achado sobre contas de teste via SQL bruto (não afeta contas reais)
Ao testar o login de verdade no navegador, uma conta de teste criada via `INSERT` direto em `auth.users` (mesma técnica de 1.1/1.2 para testes de RLS) falhava com erro 500 do GoTrue: colunas como `confirmation_token` precisam ser string vazia (`''`), não `NULL` — o scanner Go do GoTrue não aceita `NULL` nessas colunas mesmo sendo nullable no schema. **A conta real do usuário (criada pelo Dashboard) não tem esse problema** — o fluxo do Dashboard já preenche esses campos corretamente; isso só afeta contas fabricadas via SQL bruto para teste, que é exatamente por isso que a Task 6 de 1.1 nunca tentou esse caminho para a conta real.

1. **Code review** — estrutura de rotas limpa (route group `(dashboard)`, `lib/` separando supabase/tenant/permissions/nav), Server Components + Server Actions usados corretamente (sem client-side leak de lógica de permissão, conforme coding-standards.md §3). 2. **Testes** — verificação real em navegador (não só build): login, logout, e as duas direções do RBAC no menu (oculta para `atendente`, aparece para `operador`) — confirmado com evidências concretas de árvore de acessibilidade antes/depois. **Falta automação** — ver TEST-003/TEST-004.
3. **Acceptance criteria** — 5/5 ACs atendidas e demonstradas, não só implementadas.
4. **Sem regressão** — N/A (greenfield).
5. **Performance** — build de produção limpo, First Load JS ~103kB por rota — dentro do esperado para um shell sem lógica de negócio ainda.
6. **Segurança** — `middleware.ts` bloqueia corretamente rota não-pública sem sessão; `switchTenant` valida pertencimento ao tenant antes de setar o cookie (defesa em profundidade, não confia só na RLS). 3 vulnerabilidades HIGH em dependências transitivas do Next 15 — aceitas com justificativa técnica válida (SEC-002), não código do produto.
7. **Documentação** — 3 correções reais documentadas com causa raiz (versão do Next, config do ESLint, bug de RLS/query) — nível de detalhe permite a qualquer pessoa entender o "porquê", não só o "o quê".

**Achado positivo a registrar:** o bug de `getUserTenants()` (RLS de tenant mostrando colegas como se fossem tenants duplicados do próprio usuário) só foi encontrado porque o @dev testou em navegador real com um cenário de dois usuários no mesmo tenant — reforça que a prática de teste manual real, e não só `build`/`lint`, está entregando valor concreto nesta pipeline.
