## Story
**Como** gateway de canal,
**quero** capturar todo webhook recebido (corpo cru + headers) e garantir idempotência por `wa_message_id` antes de qualquer processamento,
**para que** nenhuma mensagem duplicada gere resposta duplicada e nenhum payload recebido se perca, mesmo em caso de falha downstream (NFR5: perda de mensagem inbound = 0).

## Acceptance Criteria
1. Toda requisição de webhook (UAZAPI ou Meta) é gravada em `webhook_capturas` (corpo, headers, provider, `hmac_ok`) antes de qualquer outra lógica — inclusive quando a mensagem será descartada.
2. Resposta `200 OK` é devolvida imediatamente ao provider; todo processamento (identificação, debounce, IA) ocorre em background (AC 14.1–14.7, regra C5 de §14.4).
3. Idempotência garantida por índice único em `mensagens.wa_message_id` — mesma mensagem chegando duas vezes resulta em uma única linha (AC 14.6).
4. Rota de webhook isenta de rate limit (C7) e isenta de auth de sessão — autenticação é M2M via token na URL (UAZAPI) ou HMAC (Meta, tratado na story do adapter Meta).
5. Mensagem duplicada é descartada silenciosamente, sem alerta (§21.2: "Mensagem duplicada | Descarta silenciosamente | Nada | Não").

## Dev Notes

### Schema (fonte literal: PRD §17.3, §17.5)
```sql
create table webhook_capturas (
  id bigserial primary key,
  tenant_id uuid references tenants(id) on delete set null,
  provider canal_provider,
  metodo text, url text,
  headers jsonb, corpo text,
  hmac_ok boolean,
  criado_em timestamptz not null default now()
);

create unique index mensagens_wamid on mensagens(wa_message_id) where wa_message_id is not null;
```
Nota: `mensagens` é criada na story 4.x (pipeline de atendimento) — o índice de idempotência é declarado aqui como parte do contrato desta story, mas a migration física da tabela `mensagens` completa pertence à story do motor de IA (4.3, PRD S-15) ou pode ser antecipada nesta story se o @dev preferir uma única migration para a tabela — decisão de implementação, não de produto.

### Por que antes dos adapters concretos (S-05, S-06)
Ambos os adapters (2.3 e 2.4) vão *usar* esta captura e este índice de idempotência — construir depois duplicaria a lógica de captura por adapter. Ordem recomendada pelo @sm, não determinação do PRD.

### Pipeline de referência (§8.3, etapas 1–3)
```
1. Webhook recebe → responde 200 imediatamente
2. Valida assinatura (HMAC Meta) ou token (UAZAPI)
3. Idempotência por wa_message_id → descarta duplicata
```
